## 1. 기술 스택 선택지 비교

**전제**: 초중급 개발자, GitHub Pages(정적 호스팅) 배포, 게임/학습/포트폴리오 3개 섹션.

### 한눈에 보는 비교표

| 항목 | (a) 순수 HTML/CSS/JS | (b) React/Next.js | (c) Astro | (d) Vite + 바닐라/React |
|---|---|---|---|---|
| **학습 난이도** | ★☆☆ 가장 쉬움 | ★★★ 높음 | ★★☆ 중간 (HTML 알면 쉬움) | ★★☆ 중간 |
| **초기 설정** | 없음 (파일만 만들면 됨) | `create-next-app` + 정적 export 설정 필요 | `npm create astro@latest` | `npm create vite@latest` |
| **빌드 과정** | 불필요 | 필요 (`next build` + `output: 'export'`) | 필요 (`astro build`) | 필요 (`vite build`) |
| **JS 번들 크기** | 내가 쓴 만큼만 | 큼 (수백 KB 기본 탑재) | 매우 작음 (기본 0에 가까움) | 작음~중간 |
| **GitHub Pages 궁합** | 완벽 | 가능하지만 설정 함정 많음 (`basePath`, 이미지 최적화 비활성화) | 좋음 (`base` 옵션 한 줄) | 좋음 (`base` 옵션 한 줄) |
| **멀티 페이지 관리** | 수동 복붙 (공통 헤더 관리 고통) | 라우터가 해결 | 파일 기반 라우팅 + 레이아웃 컴포넌트 | 멀티 엔트리 설정 or React Router |
| **게임(Canvas) 개발** | 최적 | 오히려 방해될 수 있음 | 아일랜드로 격리 가능 | 최적 (바닐라 JS 게임 + 모듈 시스템) |
| **취업 포트폴리오 어필** | 낮음 | 높음 (React 수요) | 중간~높음 (상승 중) | 중간 (React 쓰면 높음) |

### 각 선택지 상세

**(a) 순수 HTML/CSS/JS 정적 사이트**
- 장점: 배포가 곧 파일 업로드. 디버깅이 단순하고, 게임 로직(Canvas API)에 집중 가능. GitHub Pages에 그대로 올리면 끝.
- 단점: 페이지가 5개를 넘어가면 공통 헤더/푸터 복붙 지옥. 컴포넌트 재사용 불가.
- 추천 상황: "일단 이번 주에 뭔가 띄우고 싶다"면 이걸로 시작해도 전혀 늦지 않음.

**(b) React/Next.js**
- 장점: 생태계 최대, 취업 시장에서 가장 요구됨. shadcn/ui 등 컴포넌트 자산 활용 가능.
- 단점: 2026년 비교 테스트 기준 Astro 대비 수십 배 큰 JS를 배송([Tech Insider: Astro 9KB vs Next.js 463KB](https://tech-insider.org/astro-vs-nextjs-2026/)). GitHub Pages 배포 시 `output: 'export'`, `basePath`, `images.unoptimized: true` 등 함정이 많음. 정적 콘텐츠 위주 사이트엔 과함.
- 추천 상황: 이미 React를 배우는 중이거나, 나중에 SaaS급 확장이 목표일 때.

**(c) Astro** ⭐ 이 프로젝트의 1순위 추천
- 장점: `.astro` 문법이 사실상 HTML 확장이라 진입장벽이 낮음. 기본적으로 JS를 거의 안 보내서 로딩이 매우 빠름(LCP/TTI 우수). 페이지별로 필요한 곳에만 React/바닐라 "아일랜드"를 심을 수 있음 → **포트폴리오·학습 페이지는 정적으로, 게임만 인터랙티브 아일랜드로** 구성하기에 이상적. 내부적으로 Vite 기반이라 개발 서버도 빠름.
- 단점: 실시간 대규모 상태 공유가 필요한 앱에는 부적합(이 프로젝트엔 해당 없음).
- 추천 상황: 콘텐츠(포트폴리오, 학습 자료) + 부분 인터랙션(게임)의 혼합 사이트 — 정확히 이 프로젝트.
- 참고: [Astro vs Next.js 정적 사이트 비교](https://eastondev.com/blog/en/posts/dev/20251202-astro-vs-nextjs-static-site/), [Contentful 비교 글](https://www.contentful.com/blog/astro-next-js-compared/), [Pagepro 2026 비교](https://pagepro.co/blog/astro-nextjs/)

**(d) Vite + 바닐라 JS(또는 React)** ⭐ 게임 중심이면 2순위 추천
- 장점: 게임을 바닐라 JS + Canvas로 만들면서도 모듈 시스템, HMR(즉시 반영), TypeScript, 번들 최적화를 누릴 수 있음. `vite.config.js`에 `base: '/저장소명/'` 한 줄이면 GitHub Pages 대응 완료.
- 단점: 멀티 페이지는 `rollupOptions.input`에 엔트리를 직접 등록해야 함(어렵지 않음).
- 참고: [Vite 공식 정적 배포 가이드](https://vite.dev/guide/static-deploy)

### 결론 (추천 시나리오)

| 상황 | 추천 |
|---|---|
| 최대한 빨리 결과물 | 순수 HTML/CSS/JS → 나중에 Astro로 이관 |
| 콘텐츠+게임 혼합, 성능·구조 둘 다 | **Astro** (게임 부분은 바닐라 JS 아일랜드) |
| React 학습 겸용 | Vite + React (Next.js보다 Pages 배포가 단순) |
| 게임이 사이트의 90% | Vite + 바닐라 JS/TS |

## 2. 무료 배포 플랫폼 비교

### 비교표 (2026년 무료 티어 기준)

| 항목 | GitHub Pages | Vercel | Netlify | Cloudflare Pages |
|---|---|---|---|---|
| **가격** | 완전 무료 (공개 저장소) | Hobby 무료 | 무료 (크레딧제 전환) | 무료 |
| **대역폭** | 월 100GB (소프트 리밋) | 월 100GB | 월 100GB (크레딧 소진 시 중단) | **무제한** |
| **빌드** | GitHub Actions 무료 분 사용 | 월 6,000분 수준 | 크레딧 기반 | 월 500회 |
| **서버리스 함수** | ❌ 없음 | ✅ (제한적) | ✅ (제한적) | ✅ Workers 연동 |
| **커스텀 도메인** | ✅ (CNAME 파일) | ✅ | ✅ | ✅ |
| **HTTPS 자동** | ✅ | ✅ | ✅ | ✅ |
| **상업적 이용** | 제한 (약관상 비상업 권장) | ❌ Hobby 플랜 금지 | 제한적 | ✅ 허용 |
| **저장소 크기 제한** | 1GB, 파일당 100MB | - | - | 파일 25MB |
| **초심자 난이도** | ★☆☆ 가장 쉬움 | ★☆☆ 쉬움 | ★☆☆ 쉬움 | ★★☆ 보통 |

핵심 요약 ([DanubeData 2026 비교](https://danubedata.ro/blog/cloudflare-pages-vs-netlify-vs-vercel-static-hosting-2026), [무료 정적 호스팅 8종 비교](https://htmlpub.com/blog/static-site-hosting-comparison-2026)):
- **GitHub Pages**: 코드 저장소 = 배포처. 포트폴리오 URL로 `username.github.io`가 갖는 "개발자다움"도 무시 못 함. 정적 파일만 가능.
- **Cloudflare Pages**: 무료 티어 스펙 최강(무제한 대역폭). 트래픽이 터져도 안 죽음. 나중에 D1(SQLite), KV, R2로 확장 가능.
- **Vercel**: Next.js를 쓴다면 최고의 경험. 단, Hobby 플랜은 상업적 이용 금지.
- **Netlify**: 폼(Forms) 기능이 무료라 문의 폼에 유용. 2026년 크레딧제 전환으로 무료 한도 관리가 필요해짐.

**전략 추천**: GitHub Pages를 메인으로 시작 → 트래픽/기능 필요 시 같은 저장소를 Cloudflare Pages에 연결(둘 다 무료, 이중화 효과).

### 커스텀 도메인 연결 (GitHub Pages 기준)

1. 도메인 구매: [Cloudflare Registrar](https://www.cloudflare.com/products/registrar/) (원가 판매, `.com` 연 $10 내외), [Namecheap](https://www.namecheap.com/), [Porkbun](https://porkbun.com/)
2. DNS 설정: `www` → CNAME `username.github.io`, 루트(apex) → A 레코드 4개 (`185.199.108.153` ~ `185.199.111.153`)
3. 저장소 Settings → Pages → Custom domain 입력 → **Enforce HTTPS** 체크
4. 공식 문서: [GitHub Pages 커스텀 도메인 가이드](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site)
5. 팁: 학생이라면 [GitHub Student Developer Pack](https://education.github.com/pack)으로 `.me` 도메인 1년 무료.

### 배포 자동화: GitHub Actions

저장소 Settings → Pages → Source를 **"GitHub Actions"** 로 설정 후, `.github/workflows/deploy.yml` 생성:

```yaml
name: Deploy to GitHub Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }   # Astro/Vite는 dist, Next.js export는 out
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

- `main`에 push할 때마다 자동 빌드·배포. 순수 HTML이면 워크플로 없이 Settings에서 브랜치 배포만 켜면 됨.
- 참고: [Vite 공식 GitHub Pages 배포 문서](https://vite.dev/guide/static-deploy#github-pages), [Astro GitHub Pages 배포 문서](https://docs.astro.build/en/guides/deploy/github/), [실전 예제 저장소](https://github.com/sitek94/vite-deploy-demo)
- **흔한 함정**: 프로젝트 페이지(`username.github.io/repo명`)는 `base`(Vite/Astro) 또는 `basePath`(Next.js)를 `/repo명/`으로 설정하지 않으면 CSS/JS가 404남.

## 3. 무료 백엔드 대안

### 3-1. localStorage만으로 가능한 범위 (백엔드 0원, 서버 없음)

| 가능 ✅ | 불가능 ❌ |
|---|---|
| 게임 최고 점수, 학습 진도, 오답 노트 | 사용자 간 랭킹 공유 |
| 설정(다크모드, 언어) 저장 | 기기 간 동기화 |
| 일일 스트릭(연속 학습일) | 진짜 로그인/계정 |
| 퀴즈 결과 히스토리 | 부정행위 방지 |

- 용량: 오리진당 약 **5MB** (문자열만 저장, `JSON.stringify` 필수)
- 주의: 시크릿 모드/브라우저 데이터 삭제 시 소멸. "내 기록"이라고 명확히 표기할 것.
- 패턴: 저장 스키마에 버전 필드를 넣어두면(`{v: 1, ...}`) 나중에 마이그레이션이 쉬움.
- **개인 프로젝트의 80%는 localStorage로 충분함. 백엔드는 "전체 랭킹"이 꼭 필요해질 때 도입해도 늦지 않음.**

### 3-2. Supabase vs Firebase 무료 티어 (2026)

| 항목 | Supabase Free | Firebase (Spark) |
|---|---|---|
| DB | PostgreSQL 500MB | Firestore 1GiB |
| 요청 제한 | API 요청 무제한 | 일 5만 읽기 / 2만 쓰기 |
| 인증(MAU) | 50,000명 | 무제한(기본 인증) |
| 파일 저장 | 1GB | 5GB |
| 프로젝트 수 | 2개 활성 | 다수 |
| 주의점 | **7일간 요청 없으면 프로젝트 일시정지** | 종량제 전환 시 비용 예측 어려움 |
| 개발 경험 | SQL, RLS(행 수준 보안), 자동 REST API | NoSQL, 실시간 동기화 강점 |

- 출처: [Supabase 공식 비교](https://supabase.com/alternatives/supabase-vs-firebase), [2026 무료 티어 정리](https://aiagencyplus.com/supabase-free-tier-limits/), [Tech Insider 비교](https://tech-insider.org/supabase-vs-firebase-2026/)
- **추천**: 이 프로젝트에는 **Supabase**. 이유 — ① 랭킹 = 관계형 데이터(SQL `ORDER BY score DESC LIMIT 10` 한 줄) ② 정적 사이트에서 JS SDK로 바로 호출 가능(서버 불필요) ③ SQL 경험 자체가 포트폴리오 어필 포인트.
- 7일 정지 대책: GitHub Actions로 매주 ping을 보내는 cron 워크플로를 하나 두면 됨.
- 대안: **Cloudflare D1 + Workers** (Cloudflare Pages 사용 시 자연스러운 조합), **PocketBase**(단일 실행 파일, 단 무료 상시 호스팅은 별도 필요).

### 3-3. GitHub 저장소를 DB처럼 쓰는 패턴

정적 사이트에서 의외로 강력한 무료 패턴 ([관련 아이디어 글](https://medium.com/younited-tech-blog/what-if-hosting-sources-website-and-database-on-github-8caf82d0bc07)):

| 패턴 | 방법 | 적합한 용도 |
|---|---|---|
| **읽기 전용 JSON DB** | `data/words.json`을 저장소에 커밋 → `fetch('./data/words.json')` | 단어장, 퀴즈 문제 은행, 포트폴리오 프로젝트 목록 |
| **GitHub Issues = 방명록/댓글** | [utterances](https://utteranc.es/) 또는 [giscus](https://giscus.app/) 위젯 임베드 | 방명록, 블로그 댓글 (완전 무료) |
| **Actions로 데이터 갱신** | 스케줄 워크플로가 JSON을 갱신·커밋 → 사이트 자동 재배포 | "오늘의 단어", 주간 통계 |
| **Gist API** | 공개 Gist를 fetch로 읽기 | 소규모 설정/데이터 |
| **정적 SQLite** | [sql.js-httpvfs](https://phiresky.github.io/blog/2021/hosting-sqlite-databases-on-github-pages/)로 Pages 위에서 SQLite 쿼리 | 대량 사전 데이터 검색 |

⚠️ **경고**: 브라우저에서 GitHub 토큰으로 직접 쓰기(write)하는 패턴은 토큰이 노출되므로 절대 금지. 쓰기가 필요하면 Supabase나 Cloudflare Workers를 쓸 것.

### 단계별 백엔드 로드맵

```
1단계: localStorage (개인 기록)          → 지금 바로
2단계: 저장소 JSON (콘텐츠 데이터)        → 지금 바로
3단계: giscus (방명록/댓글)              → 30분 작업
4단계: Supabase (전체 랭킹, 로그인)       → 필요해질 때
```

## 5. 정보 구조(IA) 설계안

### 콘셉트: "허브형 랜딩 + 3개의 서브 앱"

```
/                    ← 허브 랜딩: 정체성 한 줄 + 3개 섹션 카드
├── /games/              ← 게임 목록 (카드 그리드)
│   ├── /games/word-shooter/   ← 개별 게임 (풀스크린 Canvas)
│   └── /games/typing-race/
├── /learn/              ← 학습 허브 (오늘의 단어, 진도 대시보드)
│   ├── /learn/vocab/          ← 단어장 (JSON 데이터 기반)
│   └── /learn/quiz/           ← 퀴즈 (결과 공유 버튼 포함)
├── /portfolio/          ← 프로젝트 목록 + 상세 (이 사이트 자체도 항목!)
└── /about/              ← 소개 + 연락처 + 방명록(giscus)
```

### 설계 원칙

1. **허브는 3초 안에 전체가 파악되게**: 첫 화면에 "나는 누구, 이 사이트는 뭐 하는 곳" 한 줄 + 게임/학습/포트폴리오 3장의 카드. 스크롤 없이 3개 섹션 진입 가능.
2. **섹션별 성격에 맞는 레이아웃, 공통 뼈대는 유지**: 상단 네비게이션(로고 + 3메뉴)과 푸터는 전 페이지 공통. 게임 플레이 화면만 예외적으로 몰입형(네비 최소화 + "나가기" 버튼).
3. **라우팅**: 정적 호스팅이므로 **파일 기반 라우팅(폴더 = URL)** 이 가장 단순. Astro는 `src/pages/` 구조가 곧 URL. SPA(React Router)로 만들 경우 GitHub Pages 새로고침 404 문제가 있으므로 `404.html` 트릭 또는 해시 라우팅 필요 → **초중급자는 MPA(멀티 페이지) 구조 권장**.
4. **게임과 학습을 교차 연결하면 차별화**: "단어 게임의 점수 → 학습 진도에 반영", "오답 단어 → 게임에 재등장". 이 연결고리가 이 사이트만의 스토리가 됨.

### 공통 디자인 시스템 (최소 구성)

```css
/* tokens.css — 모든 페이지가 공유 */
:root {
  --color-primary: #6366f1;   /* 브랜드 컬러 1개 */
  --color-accent-game: #f59e0b;   /* 섹션 식별 색 */
  --color-accent-learn: #10b981;
  --color-accent-folio: #6366f1;
  --font-body: "Pretendard Variable", sans-serif;
  --radius: 12px;
  --shadow-card: 0 4px 12px rgb(0 0 0 / 0.08);
}
```

- 규칙: 브랜드 컬러 1개 + 섹션 포인트 컬러 3개 + 중립 회색 스케일. 폰트는 1종(Pretendard, 굵기로 위계 표현). 카드/버튼/간격 스타일을 전 섹션에서 동일하게.
- 다크모드는 `prefers-color-scheme` + CSS 변수 스왑으로 처음부터 설계하면 나중에 공짜.

## 6. AI 도구 활용 워크플로

### Claude Code로 사이트 개발하기

효율적인 워크플로 ([Claude Code 프론트엔드 가이드](https://medium.com/@satnammca/how-to-set-up-claude-code-for-frontend-development-the-complete-guide-118463a5d22e), [디자이너를 위한 Claude Code 2026](https://www.925studios.co/blog/2026-03-18-claude-code-for-designers-the-complete-guide-to-building-real-websites-in-2026)):

1. **CLAUDE.md를 프로젝트 헌법으로**: 저장소 루트에 기술 스택, 폴더 구조, 디자인 토큰, "하지 말 것"(예: 외부 CDN 남용 금지)을 적어두면 매 세션 일관된 결과.
2. **픽셀 지정 대신 방향 제시**: "마진 24px, #6366f1"보다 "어학 학습 사이트답게 차분하고 신뢰감 있게, 게임 섹션만 에너지 있게" 같은 목적·톤 중심 프롬프트가 더 좋은 결과를 냄.
3. **스크린샷 피드백 루프**: 결과물을 캡처해서 붙여넣고 "이 부분이 답답해 보임" 식으로 반복 수정 — 프론트엔드에서 가장 효율적인 루프.
4. **작업 단위는 기능 1개씩**: "사이트 전체 만들어줘"보다 "단어 퀴즈의 채점 로직 → 결과 화면 → 공유 버튼" 순서로. 커밋도 그 단위로.
5. **테스트/배포까지 맡기기**: GitHub Actions 워크플로 작성, Lighthouse 점수 개선, 접근성 감사 같은 반복 작업이야말로 AI에 위임하기 좋은 영역.

## 7. "대박" 사이트 체크리스트

### 첫인상 3초

- [ ] 첫 화면(스크롤 전)에 **"이 사이트가 뭔지" 한 문장** + 핵심 행동 버튼 1개 ("게임 시작하기")
- [ ] 히어로에 움직임 하나 (미묘한 애니메이션, 타이핑 효과 등 — 단 1개만)
- [ ] 파비콘 + 브라우저 탭 제목 설정 (의외로 안 하는 사람 많음)
- [ ] 방문 즉시 플레이 가능한 요소 (회원가입 요구 없이 게임 1판, 퀴즈 3문제)

### 로딩 속도 (Core Web Vitals, 2026 기준)

| 지표 | 목표 | 실전 방법 |
|---|---|---|
| LCP | **2.0초 이내** (2026년 기준 강화) | 히어로 이미지 WebP/AVIF + `fetchpriority="high"`, 나머지는 `loading="lazy"` |
| INP | 200ms 이내 | 게임 루프에서 메인 스레드 블로킹 금지, 무거운 연산은 분할 |
| CLS | 0.1 이하 | 모든 이미지에 `width`/`height` 명시, 폰트는 `font-display: swap` |

- 측정: [PageSpeed Insights](https://pagespeed.web.dev/) + Chrome DevTools Lighthouse. 배포할 때마다 확인하는 습관.
- 참고: [Core Web Vitals 2026 체크리스트](https://www.corewebvitals.io/core-web-vitals/ultimate-checklist), [Google 공식 문서](https://developers.google.com/search/docs/appearance/core-web-vitals)
- 정적 사이트 + Astro/바닐라 조합이면 사실상 90점대가 기본값 — 이것이 1장에서 가벼운 스택을 추천한 이유.

### 모바일 최적화

- [ ] 개발 중 항상 DevTools 모바일 뷰 우선 확인 (방문자 대다수는 모바일)
- [ ] 터치 타깃 최소 44×44px, 게임은 터치 조작 지원 (버튼/스와이프)
- [ ] `<meta name="viewport" content="width=device-width, initial-scale=1">` 필수
- [ ] 게임 화면 가로/세로 모드 대응 또는 안내
- [ ] PWA 매니페스트 추가 시 "홈 화면에 추가" 가능 → 앱처럼 사용 (선택이지만 강력)

### 공유하고 싶게 만드는 요소

- [ ] **OG 태그 4종 필수**: `og:title`, `og:image`, `og:url`, `og:type` + `twitter:card` — 없으면 카톡/디스코드 공유 시 깨진 미리보기로 클릭률 급락 ([OG 이미지 가이드 2026](https://myogimage.com/blog/og-image-size-meta-tags-complete-guide))
- [ ] OG 이미지 **1200×630px**, 1MB 이하, 텍스트는 크게 (모바일 미리보기에서 읽혀야 함)
- [ ] **결과 공유 버튼**: 퀴즈/게임 결과를 이모지 그리드나 점수 카드로 만들어 Web Share API(`navigator.share`) + 클립보드 복사 폴백 — Wordle式 공유가 무료 마케팅의 핵심
- [ ] 공유 문구에 궁금증 유발 장치 ("나는 상위 12%였다. 너는?")
- [ ] 미리보기 검증: 카카오톡은 [카카오 디버거](https://developers.kakao.com/tool/debugger/sharing), 기타는 [OpenGraph.xyz](https://www.opengraph.xyz/)
- [ ] 매일 돌아올 이유 1개: 오늘의 단어, 일일 퀴즈, 스트릭(연속 기록)

### 마지막 디테일

- [ ] 404 페이지도 재미있게 (미니게임 이스터에그면 그 자체로 공유거리)
- [ ] 키보드만으로 조작 가능한지 확인 (접근성 = 완성도의 증거)
- [ ] `robots.txt` + `sitemap.xml` (Astro는 플러그인으로 자동 생성)
- [ ] README에 스크린샷 + 라이브 링크 — 저장소 자체가 포트폴리오의 일부
